01

이해관계자 가치 & Pain Point

Agile과 MSA 방식이 없다면 각 이해관계자가 실제로 무엇을 못 하는지 먼저 정의하고, 그 문제가 왜 중요한지, 이 두 기술이 어떤 가치로 바뀌는지 짚는다.

MVPMVP는 어떤 경우에 적용되나

이 플랫폼의 최소 가치 제품(MVP)은 "수강생이 강의를 찾아 수강신청하고 결제까지 완료하는 것"이다. 추천은 이 핵심 거래 위에 얹히는 부가 가치이며, 규칙(최빈 카테고리·인기순)이 실제로 사용자 행동을 바꾸는지 검증이 필요한 가설이다. 즉 MVP는 "요구사항의 완결"이 아니라 "가장 빨리 시장·사용자에게 검증받을 수 있는 최소 단위"이며, 다음 조건에서 특히 유효하다.

  • 가설 검증이 필요할 때 — "카테고리 기반 추천이 재수강률을 높이는가?"처럼 만들어봐야 아는 기능.
  • 요구사항이 유동적일 때 — 추천 규칙은 운영하며 계속 바뀐다. 처음부터 정교한 ML을 만들면 낭비.
  • 빠른 출시가 경쟁력일 때 — 핵심 거래(수강+결제)를 먼저 내보내고, 추천은 뒤이어 반복 개선.

Agile·MSA가 없다면 — 이해관계자별 Pain Point

추천까지 한 덩어리(모놀리식)로, 요구사항을 전부 확정한 뒤 한 번에(빅뱅) 만든다고 가정하면 다음이 발생한다.

경영진

검증 지연·리스크 집중

Pain — 추천까지 다 만들어야 출시되므로 시장 검증이 몇 달 늦어지고, 잘못된 가설에 큰 비용이 한꺼번에 묶인다.

강의운영·기획 담당자

규칙 실험 불가

Pain — 추천 규칙 한 줄을 바꿔 A/B 하려 해도 전체 재배포·전체 회귀테스트가 필요해, 운영자가 실험을 주도할 수 없다.

기술 책임자

장애 전파·기술 고착

Pain — 결제 모듈 하나가 죽으면 수강신청·추천까지 동시에 내려가고, Python 추천 로직과 Java 코어를 한 프로세스에 섞을 수 없다.

수강생 (최종 사용자)

탐색 피로·불안정

Pain — 수백 개 강의에서 뭘 들을지 스스로 찾아야 하고, 결제 트래픽 폭주 때 수강신청 화면까지 함께 느려진다.

02

이를 해결하는 AI 솔루션

Pain Point를 "개인화 추천으로 탐색 부담을 줄이고, 추천을 독립적으로 빠르게 실험할 수 있게 한다"로 재정의하고, 규칙기반 추천 업무 서비스를 기획한다.

AI 업무 서비스 — 규칙기반 강의 추천

recommend-service(Python/FastAPI, :8085)는 자체 DB 없이 다른 서비스의 API를 조합해 추천을 만든다. 제공된 recommend_service.py의 규칙은 다음과 같다.

추천 규칙 (rule-based)

① 사용자의 ACTIVE 수강 이력 조회 → ② 수강 강의들의 최빈 카테고리 산출(Counter.most_common) → ③ 그 카테고리의 미수강 강의를 수강생 수 내림차순으로 정렬 → ④ 최대 5개 반환. 수강 이력이 없는 신규 사용자는 전체 인기순(enrollmentCount)으로 대체(cold-start).

핵심 기능과 Agile·MSA의 역할

핵심 기능Agile의 역할MSA의 역할
수강 이력 기반 카테고리 추천User Story로 가치 정의 후 Sprint에서 규칙을 점진 정교화enrollment·course API를 조합, 추천은 독립 서비스로 분리
신규 사용자 인기순 추천cold-start를 별도 스토리로 분리해 우선순위 판단동일 서비스 내 분기 처리, 다른 서비스에 영향 없음
수강 완료 시 추천 갱신"실시간성"을 후속 스프린트 개선 항목으로 배치enrollment.completed Kafka 이벤트를 구독(느슨한 결합)
추천 규칙 교체·실험스프린트마다 규칙 변경을 안전하게 릴리스recommend-service만 재배포 → 무중단 실험

요약

Agile은 "추천이 정말 가치 있는가"라는 가설을 작은 단위로 검증·개선하는 일하는 방식을 맡고, MSA는 그 추천을 코어 거래와 분리해 독립적으로 배포·확장·격리할 수 있는 구조를 맡는다.

03

아키텍처 구성도

경영진·업무 담당자·기술 책임자가 "이 솔루션이 기술적으로 어떻게 동작하는가"를 한눈에 이해하도록, 전체 파이프라인과 세 가지 핵심 질문에 대한 답을 구성한다.

Q1Backlog 우선순위 & Sprint 1 / Sprint 2 분할 기준

User Story에서 백로그를 도출하고, ① 비즈니스 가치(핵심 거래 > 부가가치) ② 의존성(선행 서비스 먼저) ③ 리스크 순으로 우선순위를 매긴다. 이 세 축이 곧 Sprint 경계를 만든다.

분할 원칙

Sprint 1 = "동작하는 최소 거래 파이프라인(MVP)" — 수강신청→결제가 끝까지 흐르는 것. Sprint 2 = "AI 부가가치" — 그 위에 추천을 얹고 이벤트로 갱신. 추천은 코어에 의존하므로 뒤에 온다.

Q2MSA 분할 원칙 & 트랜잭션 격리

분할 기준 — 업무(데이터 생성/처리) 단위. 업무 결과는 데이터로 남으므로, 코드 템플릿은 "누가 그 데이터를 소유하고 변경하는가"로 서비스를 나눴다. 각 서비스가 자기 테이블만 책임진다.

핵심

같은 enrollments 데이터를 다루는 트랜잭션(수강 생성 vs 활성화)은 서로 다른 서비스로 쪼갤 수 없다 — 데이터 정합성 때문에 enrollment-service 한 곳이 소유해야 한다. 그럼 한 서비스 안에서 이 트랜잭션들을 어떻게 격리하는가?

서비스 내부 트랜잭션 격리 — 코드에 적용된 4가지 기법:

  1. 읽기/쓰기 경계 분리 — EnrollmentService는 클래스 레벨 @Transactional(readOnly=true)가 기본. 쓰기는 명시적으로만 열린다.
  2. 독립 트랜잭션(REQUIRES_NEW) — PENDING 수강 생성은 별도 빈 EnrollmentWriteService로 분리해 즉시 커밋. 이후 외부 결제 호출이 실패해도 생성 트랜잭션은 롤백되지 않는다(경계 격리).
  3. DB 동시성 제약 — UNIQUE KEY uq_user_course(user_id, course_id)로 동시 중복 수강신청을 DB 레벨에서 차단.
  4. 서비스 간 최종 일관성(Saga) — 활성화는 강한 결합 대신 payment.completed Kafka 이벤트를 소비해 별도 @Transactional로 수행.

enrollment-service/.../service/EnrollmentWriteService.java

// (2) 반드시 독립 트랜잭션 — 외부 결제 호출과 커밋 경계를 분리
@Transactional(propagation = Propagation.REQUIRES_NEW)
public Enrollment createPendingEnrollment(Long userId, Long courseId) {
    return enrollmentRepository.save(
        Enrollment.builder().userId(userId).courseId(courseId).build());
}

enrollment-service/.../service/EnrollmentService.java

@Transactional(readOnly = true)   // (1) 클래스 기본 = 읽기 전용
public class EnrollmentService {
  public EnrollmentResponse enroll(Long userId, Long courseId) {
    // ... 강의 존재/중복 확인 (읽기)
    Enrollment e = enrollmentWriteService.createPendingEnrollment(userId, courseId); // 독립 커밋
    paymentServiceClient.requestPayment(userId, courseId, ...);  // 외부 동기 REST
  }
  @Transactional // (4) 활성화는 별도 쓰기 트랜잭션 — Kafka consumer가 호출
  public void activateEnrollment(Long userId, Long courseId) { /* PENDING→ACTIVE */ }
}

Q3식별·인증·통신을 위한 인프라 특성 (완성형 제공)

분할된 MSA들은 서로 식별하고, 인증하고, 통신해야 한다. 이 인프라는 실습 대상이 아니며 완성형으로 제공된다 (실무에서도 신입에게 인프라 구축까지 맡기지 않는다). 코드에서 확인되는 특성은 다음과 같다.

관심사인프라 특성코드 근거

한 줄 정리

Eureka=식별, Gateway+OAuth2/JWT+JWKS=인증, REST+Kafka=통신. 이 세 축이 완성형으로 깔려 있기에, 실습에서는 그 위에서 비즈니스 서비스(특히 추천)만 Agile하게 얹으면 된다.

04

트러블슈팅

실습 중 겪은 이슈·새 용어·요소기술 연결을 기록하는 칸. 아래는 제공 코드에서 실제로 마주칠 지점을 예시로 채워둔 것이며, 본인 경험으로 갱신한다.

예시 · Kafka 이벤트 역직렬화

EnrollmentKafkaConsumer가 특정 DTO가 아니라 Map<String,Object>로 이벤트를 받는 이유 — payment-service가 type 헤더 없이 JsonSerializer로 발행하므로, 소비 측이 타입을 강제하면 역직렬화가 깨진다. → 서비스 간 이벤트는 스키마 계약이 느슨할 수 있음을 체감.

예시 · 기동 순서 & ARM64

depends_on: condition: service_healthy가 없으면 DB/Kafka/Eureka보다 서비스가 먼저 떠 연결 실패. 또한 학생용은 platform: linux/arm64 사전 빌드 이미지를 docker load로 올려 --pull never로 기동.

예시 · JWKS 공개키 검증

recommend-service가 토큰의 kid로 JWKS에서 공개키를 찾아 RS256 서명 검증(_jwks_cache). → 각 서비스가 auth-server에 매번 묻지 않고 무상태로 자기 검증하는 MSA 인증 패턴 이해.

직접 작성 칸

겪은 문제 · 원인 · 해결 · 배운 점을 여기에 기록.
